# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MCP server that helps users design Renovate configurations interactively. TypeScript, Node ≥ 24 (aligns with Renovate's own engine requirement), built with `@modelcontextprotocol/sdk` 1.x, stdio transport.

Surface is intentionally small: fourteen tools (`check_setup`, `read_config`, `suggest_presets`, `resolve_config`, `explain_config`, `resolve_config_diff`, `preview_custom_manager`, `validate_config`, `lint_config`, `dry_run`, `dry_run_diff`, `migrate_config`, `write_config`, `get_version`) plus the `renovate://presets` resource family (namespace index, per-namespace listings, per-preset JSON). Don't grow this without a reason — the roadmap for expansion lives in the GitHub issues, not in ad-hoc additions.

## Commands

```bash
npm install
npm run typecheck         # tsc --noEmit (covers src + test)
npm run build             # tsc -p tsconfig.build.json → dist/
npm run dev               # build watch mode
npm start                 # run built server over stdio
npm test                  # vitest run (auto-builds via pretest)
npm run test:watch        # vitest watch mode
npm run test:coverage     # vitest run --coverage (writes coverage/ report)
npm run generate:presets  # regenerate src/data/presets.generated.ts
npm run generate:managers # regenerate src/data/managers.generated.ts
npm run generate:migrations # regenerate src/data/migrations.generated.ts
```

Run a single test file: `npx vitest run test/unit/configLocations.test.ts`. Filter by name: `npx vitest run -t "renovate.json5"`.

Two tsconfigs: the root `tsconfig.json` includes both `src/` and `test/` and is used by `typecheck`; `tsconfig.build.json` narrows to `src/` only and is what `build` uses so tests never leak into `dist/`.

## Architecture — the non-obvious bits

**Shell out to the Renovate CLI at runtime; never import `renovate` as a library in `src/` from the main process.** Every tool that needs Renovate goes through `src/lib/renovateCli.ts`, which resolves the binary name (overridable via `RENOVATE_BIN` / `RENOVATE_CONFIG_VALIDATOR_BIN` env vars) and spawns it as a child process. Importing `renovate` from the main server process is the wrong pattern — the whole runtime design hinges on staying decoupled from Renovate's API surface. Exceptions:
- Build-time scripts under `scripts/` may import Renovate to generate committed snapshots — see the preset catalogue.
- **Worker-thread isolation is an explicit carve-out** for tools that need a Renovate library export with no CLI equivalent. `migrate_config` does this via `src/lib/migrationWorker.ts` + `src/lib/migrationWorkerImpl.ts`: the main process spawns a worker on demand; the worker imports `renovate/dist/config/migration.js`; the main process itself never imports `renovate`. See `docs/adrs/0001-worker-isolated-renovate-migration.md` for the rationale. `resolve_config` / `explain_config` use the same shape for their faithful config merge via `src/lib/mergeWorker.ts` + `src/lib/mergeWorkerImpl.ts`, which import `renovate/dist/config/utils.js` (`mergeChildConfig`) in the worker. Future tools wanting the same shape need their own ADR.

**Each tool is a `register<Name>(server)` function in its own file** under `src/tools/`. `src/index.ts` wires them all into a single `McpServer` instance. Same pattern for resources under `src/resources/`.

**Config-file discovery lives in `src/lib/configLocations.ts`** and mirrors Renovate's own priority order (`renovate.json`, `renovate.json5`, `.github/renovate.json`, `.gitlab/renovate.json`, `.renovaterc*`, then `package.json#renovate`). `read_config` and `write_config` both rely on this.

**`write_config` is temp-file → validate → atomic rename.** A failed validation must never leave a broken config on disk. `force: true` bypasses the validation gate but still uses the same rename path. Don't refactor this into a direct-write.

**All config writes go through `src/lib/configWriter.ts`.** The writer is the single place that constructs the bytes destined for disk. When the target file already exists and parses as JSON-with-comments (via `jsonc-parser`), the writer performs a surgical round-trip edit that preserves comments, key order, and trailing trivia. Brand-new files fall back to `JSON.stringify(config, null, 2) + "\n"` — byte-identical to pre-Phase-4 behavior. The writer refuses `.json5` files that use JSON5-only syntax (unquoted keys, single quotes, hex literals) with `reason: "json5-not-jsonc-compatible"`; corrupted JSON/JSONC files refuse with `reason: "existing-file-unparseable"`. Both refusal reasons are part of the documented user-facing contract — the README's tool table and Design notes name them verbatim. Both refusals hint at `force: true` as the destructive escape hatch; `force: true` skips both validation AND the round-trip path — the user has accepted a clean rewrite. The writer never shells out and never imports `renovate`; `jsonc-parser` is write-path-only and `src/lib/configWriter.ts` is the only place it is imported. The existing `json5` dependency stays for parse-only consumers (`migrate_config`, `lint_config`, `configLocations.ts`) — do not migrate those call sites to `jsonc-parser`. See `docs/adrs/0002-round-trip-config-writes.md` for the rationale (ADR-0002).

**`dry_run` uses `--report-type=file` with a temp report path**, reads the structured JSON report Renovate writes, and returns that rather than scraping stdout. Keeps the tool's output predictable across Renovate versions. If the report isn't produced (Renovate crashed), we fall back to surfacing the tail of stderr.

**Spawn errors never leak raw to users.** All three shell-out tools catch spawn failures and wrap them via `formatMissingBinaryError` in `src/lib/renovateCli.ts`, which also points users at the `check_setup` tool. `src/index.ts` runs `checkSetup()` at startup and, when anything's missing, appends the status to the server's `instructions` so the LLM sees the setup problem before a tool call fails.

**Integration tests use stdio + fake binaries, not mocks.** `test/helpers/mcpSession.ts` spawns `dist/index.js` as a real child process and speaks JSON-RPC over stdio — so the tests exercise the actual MCP handshake and tool registration. For code that shells out to Renovate (`write_config` rollback), the tests generate executable Node scripts (`#!/usr/bin/env node`) at runtime and point `RENOVATE_CONFIG_VALIDATOR_BIN` at them. Don't replace this with vi.mock of child_process; the whole point is that the real spawn path is tested. The per-PR CI workflow (`.github/workflows/ci.yml`) installs the pinned Renovate via `npm ci` (it's a runtime dep), but the integration tests still point at fake binaries via `RENOVATE_BIN` / `RENOVATE_CONFIG_VALIDATOR_BIN` for determinism — the real Renovate CLI is exercised end-to-end by a separate nightly workflow (`.github/workflows/nightly-real-renovate.yml`) that installs `renovate@latest` on top of `npm ci` and re-runs the full suite, catching upstream drift before a devDep bump.

**`preview_custom_manager` is offline and native — does NOT shell out.** `src/lib/customManagerPreview.ts` walks the repo directly (skipping `.git/` and `node_modules/`), applies `fileMatch` regexes to relative paths, runs each `matchStrings` entry against file content, and surfaces per-line hits with named capture groups (regex) or extracted JSONata-projection results, plus extracted dep info. It deliberately mirrors a subset of Renovate's customManager behavior: `customType: "regex"` and `customType: "jsonata"` (for `fileFormat: "json" | "yaml" | "toml"`), `matchStringsStrategy` of `any` / `combination` / `recursive` for the regex path (others warn and fall back to `any`; JSONata managers don't use `matchStringsStrategy`), and `{{groupName}}` template substitution for both paths (not full Handlebars helpers/conditionals). JSONata expressions must return either an array of objects whose keys map to dep fields OR a single bare object (auto-wrapped to a one-element array, mirroring Renovate's own `QueryResultZod`). The point is fast iterative authoring feedback; users are expected to run `dry_run` afterwards for full-fidelity confirmation. Keep this tool pure — do not route it through `renovateCli.ts`.

**`suggest_presets` is pure, offline, native — same purity class as `preview_custom_manager`.** `src/lib/presetSuggester.ts` ranks presets by lexical relevance to a free-text intent across the committed built-in catalogue (`src/data/presets.generated.ts`) and an optional local presets repo (`presetsPath`, flat `*.json`/`*.json5`, parsed with `JSON5` — the parse-only side of the json5/jsonc-parser split). No `renovate` import, no CLI, no worker, no network. The scorer is field-weighted (name>namespace>description>body) with a load-time IDF-style rarity weight so ubiquitous tokens don't drown specific matches. When coverage is weak (or ≥2 facets are recognized) it also assembles an **unvalidated** draft config from a small, hand-maintained facet taxonomy (`FACETS` in the same file) — a deliberately bounded maintenance surface, analogous to the project's other hand-maintained allow-lists. The draft is NEVER validated or merged inside the tool (that would require the CLI / merge worker and break the instant-offline property); it composes into `validate_config` / `lint_config`, the same way `preview_custom_manager` points at `dry_run`. Don't route any of this through `renovateCli.ts`, and don't call `resolveConfig` / the merge worker on the draft. See `docs/adrs/0005-suggest-presets-intent-discovery.md` for the rationale (ADR-0005, local-only).

**JSONata evaluation is worker-isolated, like the regex path.** The same `worker_threads` worker that runs user regexes also evaluates JSONata expressions via a dedicated `EvaluateJsonata` request variant. Pathological expressions are killed by `worker.terminate()` on the `matchTimeoutMs` budget (default 2 s) — identical safety posture to the regex worker. The `jsonata` npm package is `require()`'d ONLY inside the worker source string; the main process never resolves `jsonata`. This is the same isolation invariant as the regex path — `customManagerPreview.ts` itself stays free of the `jsonata` import, so the main MCP process never carries the JSONata parser in its heap. Test code under `test/` may import `renovate` to build oracle parity tests against Renovate's own JSONata extractor (see `test/unit/jsonataParity.test.ts`); `src/` never does.

**Runtime deps added for the JSONata preview path (Phase 5):** `jsonata` (pinned to exactly `2.1.0` matching Renovate's own pin — bumped only when Renovate's pin bumps, to keep the parity-test oracle stable), `yaml` (already transitive via `renovate`, now also a direct dep so a future Renovate removal cannot pull it out from under us), and `smol-toml` (caret range — no upstream pin to match). All three are lazy-loaded: `jsonata` via `require()` inside the worker source string, `yaml` and `smol-toml` via `await import()` inside `parseStructured()` in `customManagerPreview.ts`. See `docs/adrs/0003-jsonata-custom-manager-support.md` for the full rationale (ADR-0003).

**`resolve_config` never shells out to the Renovate CLI.** Built-in presets expand offline against the committed preset catalogue via `src/lib/presetResolver.ts`. The expanded presets are then merged with Renovate's real `mergeChildConfig`, run in a worker thread (`src/lib/mergeWorker.ts`) so the main process still never imports `renovate`; `explain_config` shares the same `collectMergeSteps` expansion and reconstructs per-field provenance by diffing the merge's per-step snapshots (`src/lib/configExplainer.ts`). If the worker is unavailable, both tools fall back to an in-process approximate merge and report `mergeQuality: "preview"` (otherwise `"faithful"`). External presets are opt-in through the `externalPresets: true` input: `github>` and `gitlab>` are fetched over HTTPS by `src/lib/externalPresetFetcher.ts` (auth via `GITHUB_TOKEN` / `GITLAB_TOKEN` / `RENOVATE_TOKEN` env vars, 10s timeout, per-call cache), while `bitbucket>`, `gitea>`, `local>`, and npm still land in `presetsUnresolved` with a clear reason. The default (`externalPresets` unset or `false`) performs no network I/O. Don't route any of this through `renovateCli.ts` — the fetcher is intentionally a narrow, direct HTTP client.

**Preset catalogue is a committed snapshot at `src/data/presets.generated.ts`.** Generated by `scripts/generate-presets.mjs`, which is one of three build-time scripts allowed to import from the `renovate` package (the others are `scripts/generate-managers.mjs` → `src/data/managers.generated.ts` for the `matchManagers-unknown-name` lint rule, and `scripts/generate-migrations.mjs` → `src/data/migrations.generated.ts` for the `deprecated-key` lint rule). All three are build-time only — the generated files are plain data, no runtime coupling. Regenerate after a `renovate` devDep bump with `npm run generate:presets` / `generate:managers` / `generate:migrations`. The resource layer exposes three things: `renovate://presets` (markdown namespace index), the `renovate://presets/{namespace}` template (markdown listing of one namespace's presets), and the `renovate://preset/{name}` template (a single preset's expanded JSON). Don't hand-edit the generated files — re-run the generator.

## MCP SDK usage

Use the `registerTool(name, config, handler)` and `registerResource(name, uriOrTemplate, metadata, handler)` forms (current 1.x API with structured config objects). Input schemas are zod raw shapes (plain object with zod types as values — not `z.object(...)`).

## Keep `README.md` and `docs/*.md` in sync

The user-facing docs are split across `README.md` (entry point) and a handful of long-form files under `docs/`: `docs/tools.md` (per-tool reference), `docs/security.md`, `docs/operations.md`, `docs/architecture.md`, `docs/platform-setup.md`. Treat all of them as part of the feature, not as documentation that can lag. Whenever you change any of the following, update the right file(s) in the same change:

- **Adding, removing, or renaming a tool or resource** → update the tool count in the README intro line, the one-line row in the README tool table, AND the corresponding `## <tool_name>` section in `docs/tools.md`. Renames must also update the anchor links from the README table to `docs/tools.md`.
- **Changing a tool's inputs or externally-visible behavior** (new option, changed default, new env var) → update that tool's section in `docs/tools.md` and, if the change affects the one-line row in the README table, update the row too. Security-relevant changes (new auth surface, new env var) additionally land in `docs/security.md`; operational changes (new cap, new timeout, new escape hatch) land in `docs/operations.md`; architectural changes land in `docs/architecture.md`.
- **Adding or changing env vars** (auth tokens, binary overrides, etc.) → update `docs/security.md` (canonical home for env-var precedence + warnings), `docs/platform-setup.md` (the matrix and worked example) if it's a platform token, and the short Requirements section in `README.md` if it's a new top-level env var.
- **Changing what the user needs installed** (Node version, Renovate CLI requirement for a specific tool) → update README's "Requirements".
- **Changing the release/publish flow or CI setup** → update README's "Release flow" for publish-flow changes; update `docs/development.md` for CI / snapshot / integration-test changes (the README's Development section only carries the npm-script list).
- **Touching anything that the README "Example prompts" or "Example session" demonstrate** → re-read both sections and update them. The example session is a transcript that walks through `preview_custom_manager` → `validate_config` → `dry_run` → `write_config`; if you change inputs, outputs, defaults, error shapes, or the recommended workflow ordering for any tool the transcript uses, the transcript must be updated to match. Pay special attention to: tool names (a rename breaks every line that calls them), result shapes the example narrates ("4 files, 4 line hits", "2 updates", "valid", "written atomically"), and the prose around what each step achieves. A stale example is worse than none — it teaches users a workflow that no longer works. Examples stay on the front page (README), not under `docs/`.

Refusal-reason strings on `write_config` (`json5-not-jsonc-compatible`, `existing-file-unparseable`) and the `force: true` sentinel (`confirmForce: "YES_OVERRIDE_VALIDATION"`) are part of the user-facing contract and must remain verbatim in `docs/tools.md`.

If a change doesn't touch any of those, the docs probably don't need edits. When in doubt, re-read the relevant `docs/*.md` plus the README's table row and example sections, and diff them against the change mentally before assuming it's fine.

## Roadmap

The original v1 roadmap (early GitHub issues #1–#6: `resolve_config`, tests/CI, setup diagnostics, custom manager authoring helper, full preset catalogue, npm publishing) is **complete and closed** — every one of those tools ships today. The only open GitHub issue is #12 (Renovate's own auto-generated Dependency Dashboard, not a roadmap item). Post-v1 carry-overs — external-preset breadth for `bitbucket>` / `gitea>` / `npm>`, a `renovate://docs/{topic}` resource, `package.json#renovate` round-trip writes, a multi-version nightly matrix — live in `.planning/ROADMAP.md`. Don't grow the tool surface without a tracked decision.
